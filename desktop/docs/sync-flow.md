# Sync Flow Design (Option B)

## 1. Scope & Principles
- **Storage abstraction**: `storageDriver` remains the only persistence interface. Services and UI stay untouched.
- **Offline-first**: Local writes must succeed instantly; sync operates opportunistically.
- **Append-only data**: Vouchers and ledger transactions are immutable once written; corrections happen via new records.
- **Configurable drivers**: IndexedDB is the primary driver; `localStorage` remains available as a fallback (already wired via `VITE_STORAGE_DRIVER`).

## 2. Entities to Sync
| Domain          | Records                                    | Notes |
|-----------------|---------------------------------------------|-------|
| Masters         | Ledger groups, ledgers, inventory items, categories, units, godowns | Require full CRUD sync. Soft deletes must replicate.
| Vouchers        | Sales, Purchase, Payment, Receipt           | Append-only. No edits after creation. Sync must preserve ordering.
| Ledger Transactions | Generated by posting engine (per voucher) | Derived but persisted; required for reports and balances.
| Metadata        | Storage version, last sync cursors, driver preference | Needed for coordination but not user-facing.

## 3. Sync Direction & Channels
- **Local ➜ LAN/Cloud (Push)**
  - Triggered after durable write to IndexedDB.
  - Batches grouped by entity type.
  - Includes soft-deletes (masters) and append-only inserts (vouchers/transactions).
- **LAN/Cloud ➜ Local (Pull)**
  - Periodic fetch (polling) or host-push when online.
  - Applies remote changes via the same `storageDriver` write helpers.
  - Must respect entity timestamps + version counters to avoid conflicts.

## 4. Conflict Strategy
- **Masters**
  - Use `updatedAt` + monotonically increasing `version` per record.
  - Last-write-wins if versions match; otherwise reject and queue for manual resolution (future scope).
- **Vouchers & Ledger Transactions**
  - Append-only. Conflicts resolved by ordering on `createdAt` + deterministic IDs (host authority wins if ID collision detected).
  - Duplicate detection: compare `id`; if exists, skip.
- **Soft Deletes**
  - Represented via `isActive`/`status`. Higher `updatedAt` wins.

## 5. Offline Queueing & Event Capture
- **Event source**: Enhance storage layer with hooks (Phase B3) to emit `onWrite/onDelete` events after successful local commits.
- **Queue format**: IndexedDB store (`sync_queue`) containing `{ id, entityType, payload, op, version, createdAt }`.
- **Flush logic**: Background worker drains queue when network + host connections are healthy.
- **Retry/backoff**: Exponential backoff with jitter per entity type; failures remain in queue until acknowledged.

## 6. Failure Visibility
- Maintain `syncStatus` slice (Redux) with last push/pull timestamps, pending count, last error.
- Surface status in future “Sync” settings panel (no UI change now).

## 7. Next Steps (Phase B3 prerequisites)
1. Implement event hooks around `storageDriver.write/remove` to capture mutations into the queue (without changing service APIs).
2. Build LAN/Cloud sync worker that:
   - Authenticates with host (existing network service).
   - Pushes queued records via REST/WebSocket.
   - Pulls remote diffs using last cursors.
3. Ensure sync worker can be paused/resumed and survives IndexedDB driver swaps.
